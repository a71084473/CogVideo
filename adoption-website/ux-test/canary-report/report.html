01先修正一個策略前提

原本的產品目標是「提高領養率」。但市場報告的數字說明這個目標設定需要修正—— 否則金絲雀會朝錯的方向優化。

指標(114 年度)數值意涵
全國認領養率68%不算低
新北 / 台北94% / 90%都會區已接近上限
所內死亡2,294 隻(+22%)照護壓力上升
依法人道處理664 隻(+83%)高難度個案增加
全國遊蕩犬推估141,584 隻末端解決不了源頭
「台灣現在不是『沒人領養』,而是『容易被領養的動物先被帶走,剩下的動物越來越難媒合』。」 —— 台灣流浪動物領養問題分析報告・問題診斷

1.1 因此金絲雀量的不是預約總量

主要成功指標

久候動物(≥120 天)的預約占比。認養總量在都會區已近天花板, 平台真正能貢獻的是把久候個案的機會拉高。

次要指標

測驗完成率(對應報告指出的「流程複雜性影響認養意願」)、 認養後穩定度(對應報告 KPI「六個月退養率 <5%」)。

護欄

取自報告風險表原句:「若只衝活動量,可能提高短期完成、卻增加後續退養。」 金絲雀若拉高預約量但同時拉高未校準預約,即判定失敗並回滾。

報告 KPI 要求 180 天追蹤完成率 ≥85%,但訪談說高頻追蹤讓人反感。 處理方式是延長但降頻:90 天後改為三個月一次。

4.3 過程中修掉的一個真實問題

首個 pageview 會被歸錯組

第一次執行時,「金絲雀事件全為 canary」檢查是 false。 原因是測試在首次導覽之後才寫入分組,導致第一個 visit 事件被貼到自動分配的組別。改用 addInitScript 在任何頁面程式碼執行前寫入後修正。

這雖然是測試腳本的問題,但指向一個正式上線必須遵守的設計約束: 分組必須在第一個事件送出前就決定,否則漏斗頂端會被污染, 而漏斗頂端錯了,底下所有轉換率都不可信。

4.4 出場判定

  • PASS 所有埋點正確觸發
  • PASS 護欄計算正確(對照組那 1 筆未校準預約被正確標記)
  • PASS 零 JavaScript 錯誤

判定:通過,可進入 Stage 1。

4.5 這個結果不能拿來說什麼

  • 「金絲雀 5 vs 對照 1」不是效果量,只是確認阻力點移除後路徑會通。
  • 久候動物占比在對照組顯示 100%,是因為分母只有 1——這種比率在小樣本下沒有意義。
  • Persona 的行為規則是依訪談寫死的(例如「P1 沒看到中途回饋就在第 6 題放棄」), 因此結果部分是設計的產物而非發現。

Stage 0 唯一能證明的是:分流、旗標、埋點與護欄都正常運作,可以拿去接真人流量。

5.2 回滾條件

任一條成立即停止擴大並將 rollout 設為 0:

  1. 未校準預約率 > 20%(護欄:衝動認養)
  2. 六個月退養率 ≥ 5%(報告 KPI 反向)
  3. 求助入口零使用且預約數 > 5(代表求助管道形同虛設)
  4. 中途端回報工作負荷上升(需中途端問卷,不能只看認養人端)
第 4 條特別重要。訪談中「我沒空」「我哪會記得」反覆出現; 若平台提高了認養人端轉換卻把工作推給中途,整體是負向的—— 而這件事只看認養人端的漏斗永遠看不出來。

06報告與訪談的衝突,以及平台的邊界

6.1 唯一的直接衝突:追蹤期

來源主張
市場報告追蹤期應為 180 天;KPI 為 180 天追蹤完成率 ≥85%、六個月退養率 <5%
訪談「有點像電子腳鐐」「過了一年兩年之後就不太回報了,我覺得是很容易發生的事情」

處理方式不是二選一,而是延長但降頻:新增 120 天與 180 天兩個低頻節點, 90 天後明確改為三個月一次,並在頁面寫明「回一句『都很好』就完成了,不需要照片」。 節點數從 5 個增加到 7 個(見 §03 extendTo180 對照圖)。

6.2 報告指出、但這個平台解決不了的事

① 源頭管理

報告明言「最好的領養政策,最終應該是讓需要被領養的動物變少」。 遊蕩犬 141,584 隻的問題靠媒合平台解決不了,需要熱區絕育、寵登強化與放養執法。

② 交通可近性

報告舉例瑞芳動物之家過去每日僅 4 班公車。線上諮詢能部分替代到場, 但無法取代實體互動——而訪談與各縣市流程都要求實際見面。

③ FB 演算法的結構性阻礙

訪談指出「文章裡面有連結超過兩個以上,基本上可能會降到幾乎快到零」。 平台的導流策略仍未解,需要可直接貼進 FB 的圖卡而非外部連結。

④ 公立收容所整合

本平台面向民間中途。報告顯示真正的量體在 32 處公立收容所, 若不接官方 API,影響範圍有限。

⑤ 中途端工作台

認養人端做得再好,中途端沒有省力工具就跑不動。這也是回滾條件第 4 條的由來。

可重現性

ux-test/canary-stage0.mjs(Stage 0 乾跑,EXPORT= 可匯出事件流)、 ux-test/capture-canary-shots.mjs(本報告全部截圖)、 ux-test/round2-verify.mjs(兩輪 UX 優化迴歸,固定在金絲雀組)。 儀表板在 /#/canary,可切換階段、強制分組、檢視漏斗與護欄。

本報告所有分組對照截圖皆為同一網址、同一視窗尺寸、僅切換分組的實際畫面,未經修圖。 儀表板截圖載入的是 Stage 0 實測產生的 61 筆事件。 網站中所有信任數字、捐款流向與幸福回報時間軸皆標註為示意資料,未假造任何真實認養成效。
