# 金絲雀測試計畫與 Stage 0 實測結果

以四篇中途之家訪談建立的五位領養者 Persona 做小規模實測,再依《台灣流浪動物領養問題分析報告》
規劃逐步擴大範圍。本文件同時是計畫與實作說明——分流、旗標、埋點與護欄都已寫進程式,可執行、可回滾。

---

## 一、先修正一個策略前提

原本的產品假設是「提高領養率」。但市場報告的數字說明這個目標設定需要修正:

| 指標(114 年度) | 數值 | 意涵 |
|---|---|---|
| 全國認領養率 | **68%** | 不算低 |
| 新北 / 台北 | 94% / 90% | 都會區已接近上限 |
| 所內死亡 | 2,294 隻(較前年 **+22%**) | 照護壓力上升 |
| 依法人道處理 | 664 隻(**+83%**) | 高難度個案增加 |
| 全國遊蕩犬推估 | 141,584 隻 | 末端解決不了源頭 |

報告的結論是:**「台灣現在不是『沒人領養』,而是『容易被領養的動物先被帶走,剩下的動物越來越難媒合』。」**

因此本次金絲雀的成功指標**不是預約總量**,而是:

1. **久候動物(≥120 天)的預約占比** —— 主要成功指標
2. **測驗完成率** —— 對應報告指出的「流程複雜性影響認養意願」
3. **認養後穩定度** —— 對應報告 KPI「六個月退養率 <5%」

並以報告風險表中的一句話作為護欄:**「若只衝活動量,可能提高短期完成、卻增加後續退養。」**
金絲雀若拉高預約量但同時拉高未校準預約,即判定失敗並回滾。

## 二、已實作的金絲雀基礎設施

| 模組 | 檔案 | 作用 |
|---|---|---|
| 分流 | `src/lib/canary.ts` | FNV-1a 雜湊將訪客穩定分桶(0–99),依階段 rollout% 決定金絲雀或對照組 |
| 旗標 | 同上 | 九個可獨立開關的優化項,對應兩輪 UX 測試產出 |
| 埋點 | `src/lib/funnel.ts` | 11 種事件,含 `longWait` 維度 |
| 護欄 | 同上 | 未校準預約率、求助入口是否被使用 |
| 儀表板 | `src/pages/Canary.tsx`(`/canary`) | 分組漏斗、關鍵比率、護欄狀態、階段切換 |

九個旗標:`surveillanceRelief`、`fosterCandor`、`thirdPartyTools`、`expectationCalibration`、
`midQuizFeedback`、`waitingVisibility`、`peerSupport`、`reportIncentive`、`extendTo180`。
對照組全部關閉,即回到兩輪優化前的版本;**回滾只需把 rollout 設為 0**。

儀表板本身即是報告第一優先建議的實作:
> 「建立全國一致的『認養漏斗儀表板』:統一欄位定義,追蹤上架、互動、申請、核准、完成、退養、追蹤完成率。」

報告指出官方目前未公開平均收容天數、渠道轉換率與退養率——這正是這個面板要補的洞。

### 埋點驗證

- 觸發事件類型:`visit`、`quiz_start`、`quiz_mid`、`quiz_complete`、`animal_view`、
  `calibration_view`、`booking_start`、`booking_submit`(8 種)
- 分組標記正確性:金絲雀事件全為 canary ✔、對照事件全為 control ✔
- `longWait` 維度有被記錄 ✔
- JavaScript 錯誤:0

### 過程中修掉的一個真實問題

第一次執行時,「金絲雀事件全為 canary」檢查是 **false**。原因是測試在首次導覽**之後**才寫入分組,
導致第一個 `visit` 事件被貼到自動分配的組別。改用 `addInitScript` 在任何頁面程式碼執行前寫入後修正。

這雖是測試腳本的問題,但指向一個正式上線必須注意的設計約束:
**分組必須在第一個事件送出前就決定**,否則首個 pageview 會被歸錯組,污染漏斗頂端。

### Stage 0 出場判定

| 出場條件 | 結果 |
|---|---|
| 所有埋點正確觸發 | ✔ |
| 護欄計算正確 | ✔(對照組 1 筆未校準預約被正確標記) |
| 零 JavaScript 錯誤 | ✔ |

**判定:通過,可進入 Stage 1。**

### 這個結果不能拿來說什麼

N=5、每組各 5 條路徑,而且 Persona 的行為規則是我依訪談寫死的
(例如「P1 沒看到中途回饋就在第 6 題放棄」)。因此:

- 「金絲雀組預約數 5 vs 對照組 1」**不是效果量**,只是確認阻力點被移除後路徑會通。
- 久候動物占比對照組顯示 100%,是因為分母只有 1——這種比率在小樣本下沒有意義。
- 真正的效果必須在 Stage 1 以真實使用者測量。

Stage 0 唯一能證明的是:**分流、旗標、埋點與護欄都正常運作,可以拿去接真人流量。**

## 四、逐步擴大計畫

擴散順序依市場報告的資源分布設計:全國僅 32 處公立收容所、動保人力 1,127 人,
六都(新北、台北、台中、台南、桃園、高雄)明顯高於其他縣市,因此從單點往六都推,最後才是偏鄉。

| Stage | 範圍 | Rollout | 出場條件(取自報告 KPI) | 觀察期 |
|---|---|---:|---|---|
| **0 內部乾跑** | 5 位 Persona | 100% | 埋點正確、護欄正確、零錯誤 | 已完成 |
| **1 單一中途** | 1 家合作中途,8–15 隻在養 | 5% | 久候動物預約占比高於對照組;校準完成率 ≥80%;無新增 P1 錯誤 | 4 週 |
| **2 單一縣市** | **台中市** | 25% | 90 天回報完成率 ≥85%;六個月退養率 <5%;長住動物認養量高於對照組 | 8 週 |
| **3 六都** | 新北/台北/台中/台南/桃園/高雄 | 50% | 180 天追蹤完成率 ≥85%;熟齡與特殊照護動物認養量 +30%;中途端工作負荷未上升 | 12 週 |
| **4 全國** | 含偏鄉離島 | 100% | — | — |

### 為什麼 Stage 2 選台中

報告數據顯示台中是六都中最適合的試驗場:

- 認領養率 78%,低於新北 94% 與台北 90%,**改善空間最大**
- 所內死亡率 12%,是四個主要都會區中最高,對應「難送養個案集中」
- 已有送養專車(2012 起)與「益起認養吧」友善商家認養站(2019 起),
  **既有的線下觸點可以直接承接線上媒合**,不必從零建立

新北雖然表現最好,但 94% 已接近天花板,改善訊號會被雜訊淹沒;
且新北 2025 年已自行上線 AI 媒合系統,會與本平台的效果混淆。

### 每階段的回滾條件

任一條成立即停止擴大並將 rollout 設為 0:

1. 未校準預約率 > 20%(護欄:衝動認養)
2. 六個月退養率 ≥ 5%(報告 KPI 反向)
3. 求助入口零使用且預約數 > 5(代表求助管道形同虛設)
4. 中途端回報工作負荷上升(需中途端問卷,不能只看認養人端)

第 4 條特別重要。訪談中「我沒空」「我哪會記得」反覆出現;
若平台提高了認養人端轉換卻把工作推給中途,整體是負向的。

## 五、依市場報告新增的一項變更

報告建議追蹤期為 **180 天**(180 天追蹤完成率 ≥85%、六個月退養率 <5%),
而網站原本只做到 90 天。這是真實落差,已修正:

- 新增 120 天與 180 天兩個**低頻**節點,由 `extendTo180` 旗標控制
- 但保留訪談的警告——「過了一年兩年就不太回報了」「有點像電子腳鐐」——
  因此 90 天後明確降頻為三個月一次,並寫明「回一句『都很好』就完成了,不需要照片」
- 頁面標題依旗標在「90 天支持」與「180 天支持」之間切換

這是報告與訪談唯一直接衝突的地方:報告要更長的追蹤,訪談說追蹤讓人反感。
處理方式是**延長但降頻**,而不是二選一。

## 六、報告指出、但本平台尚未處理的事

誠實列出範圍外的項目,避免高估平台能做的事:

1. **源頭管理**:報告明言「最好的領養政策,最終應該是讓需要被領養的動物變少」。
   遊蕩犬 141,584 隻的問題靠媒合平台解決不了,需要熱區絕育、寵登強化與放養執法。
2. **交通可近性**:報告舉例瑞芳動物之家過去每日僅 4 班公車。線上諮詢能部分替代到場,
   但無法取代實體互動——而訪談與各縣市流程都要求實際見面。
3. **FB 演算法**:訪談指出「文章裡面有連結超過兩個以上,基本上可能會降到幾乎快到零」,
   平台導流策略仍未解。
4. **公立收容所整合**:本平台面向民間中途。報告顯示真正的量體在 32 處公立收容所,
   若不接官方 API,影響範圍有限。
5. **中途端工作台**:認養人端做得再好,中途端沒有省力工具就跑不動。

## 七、重現方式

```bash
npm install && npm run build
npx vite preview --port 4173 --strictPort &

# Stage 0 乾跑(五位 Persona × 兩組)
node ux-test/canary-stage0.mjs

# 匯出事件供儀表板載入
EXPORT=/tmp/stage0-events.json node ux-test/canary-stage0.mjs

# 兩輪 UX 優化的迴歸驗證(固定在金絲雀組)
node ux-test/round2-verify.mjs
```

儀表板在 `/#/canary`,可切換階段、強制分組、檢視漏斗與護欄。
原型階段事件僅寫入 localStorage;正式版須改為後端事件流,並依報告建議
統一全國欄位定義,才能跨中途、跨縣市比較。
